# 24 BACKUP AND RESTORE - `backup/moodle2`

Backup and restore is one of those Moodle subsystems that is often ignored while a plugin is still being developed and only receives attention when someone duplicates an activity, imports a course into another class, or tries to restore an `.mbz` on another installation. The problem is that, at that point, we are no longer dealing with a single table that needs to be copied. Moodle has to transport an entire structure between different contexts, recreate records with new IDs, remap users, courses, groups, and files, respect the choice to include or exclude user data, and rebuild internal links that previously pointed to another installation.

That is why backup should not be treated as an `export()` function that creates a ZIP. Moodle has its own mechanism, based on plan, task, and step, which describes what enters the backup, in which hierarchy data will be serialised, and how each reference will be rebuilt during restore. When a plugin participates correctly in this architecture, course backup, import, activity duplication, and restoration on another site all use the same contract. When a plugin ignores this architecture, the result is usually a collection of failures: duplication that loses attachments, restore that points to the wrong users, or child records that still reference the old instance.

In this chapter we will evolve the `mod_checkpoint` from previous chapters, now assuming that it has configuration, learner responses, attached files, grades, and a child structure of criteria. The activity will be used to explain the complete path from `define_structure()` to `after_execute()`, including `backup_nested_element`, `annotate_ids()`, `annotate_files()`, restore mappings, user-dependent data, link encoding, and subplugins. In the end, the goal is easy to state and harder to guarantee: back up on site A, restore on site B, and still have the same activity from a functional point of view even though every internal ID may have changed.

## 24.1 What actually exists inside an `.mbz`

An `.mbz` file is not an SQL dump of the course. It is a package created by the backup subsystem containing a structured representation of the data, backup metadata, XML files for activities and sections, file information, and the physical content required for reconstruction.

This explains why opening an `.mbz` and searching for the plugin table does not work the way someone accustomed to database backups might expect. Moodle does not transport raw records; it transports a structure that will be interpreted by a restore plan.

For an activity module, for example, it is common to have an XML file specific to the activity inside the backup structure. For `mod_checkpoint`, we could have a `checkpoint.xml` containing the instance, its criteria, and responses allowed by the backup settings. Files are not simply placed inside that XML because the File API has its own representation and recovery mechanism.

## 24.2 Course backup is not site backup

The mechanism studied here is the backup of courses and parts of courses. It transports activities, blocks, formats, user data when enabled, and other components connected to the backup plan.

That is different from a complete Moodle copy containing the entire database, `moodledata`, `config.php`, installed plugins, and global configuration. An `.mbz` is not a server disaster-recovery strategy.

This distinction becomes especially important for `local` plugins, admin tools, and institutional integrations. Not every piece of global data belongs in a course backup. The existence of technical backup connection points does not mean every global table should be inserted into an `.mbz`.

## 24.3 Backup plan

The process starts with a backup plan. It represents the complete plan that will be executed to create the requested backup.

The plan knows the general settings, course, selected activities, whether users are included, and the tasks that must run. A plugin normally does not create the plan directly; it joins the plan through extension points provided by core for its plugin type.

This view matters because it prevents us from thinking of `backup_checkpoint_activity_task` as an isolated process. It is one task inside a larger plan that also processes the course, sections, roles, users, files, and other components.

## 24.4 Backup task

A task is a larger unit of work inside the plan. For activity modules, each selected instance receives its own activity task.

For `mod_checkpoint`, the class will look something like:

```
class backup_checkpoint_activity_task extends backup_activity_task {
    // ...
}
```

The task defines specific settings when necessary, adds steps, and can also participate in link encoding. Simple modules normally have a single structure step, but larger plugins may have several because not everything needs to be generated by the same XML or at the same moment.

## 24.5 Backup step

A step is the effective unit of execution inside the task. For most activities, the central part is a `backup_activity_structure_step`, responsible for producing the XML structure with plugin data.

```
class backup_checkpoint_activity_structure_step
        extends backup_activity_structure_step {

    protected function define_structure() {
        // Backup structure.
    }
}
```

Inside `define_structure()`, the developer describes elements, relationships, data sources, referenced IDs, and file areas.

## 24.6 File structure for an activity module

Inside the plugin, the files live under:

```
mod/checkpoint/
    backup/
        moodle2/
            backup_checkpoint_activity_task.class.php
            backup_checkpoint_stepslib.php
            restore_checkpoint_activity_task.class.php
            restore_checkpoint_stepslib.php
```

In Moodle 5.1, when public code is under `public/`, the physical path naturally follows the new public root, but from the plugin's point of view the structure remains `backup/moodle2/` inside the component.

The name `moodle2` is historical and is still used by the current mechanism. Do not rename it to `moodle5` just because the platform version changed.

## 24.7 The backup task

A simple task can be written like this:

```php
class backup_checkpoint_activity_task extends backup_activity_task {
    protected function define_my_settings() {
    }

    protected function define_my_steps() {
        $this->add_step(
            new backup_checkpoint_activity_structure_step(
                'checkpoint_structure',
                'checkpoint.xml'
            )
        );
    }

    public static function encode_content_links($content) {
        return $content;
    }
}
```

`define_my_settings()` remains empty when the activity does not need to add specific settings to the plan. `define_my_steps()` adds the step that will produce `checkpoint.xml`.

## 24.8 `backup_activity_structure_step`

The base class already understands that we are working with an activity and provides important helpers, especially `prepare_activity_structure()`.

This helper wraps the plugin-specific structure in the standard structure Moodle expects for an activity, so the return value is normally not simply the root element you created.

```php
return $this->prepare_activity_structure($checkpoint);
```

Ignoring this preparation can produce a structure that looks correct in isolation but does not connect properly to the rest of the course-module backup.

## 24.9 `backup_nested_element`

`backup_nested_element` represents a node in the XML tree that will be generated. You provide the element name, the fields used as identifiers, and the fields that will be serialised.

```php
$checkpoint = new backup_nested_element(
    'checkpoint',
    ['id'],
    [
        'name',
        'intro',
        'introformat',
        'questiontext',
        'questionformat',
        'grade',
        'timeopen',
        'timeclose',
        'timemodified',
    ]
);
```

The first array contains identifying attributes, normally `id`. The second contains the data that will be exported.

## 24.10 `backup_nested_element` is not a table

The element name does not have to match the table name, although it often does. The element represents the serialised structure, not an automatic `SELECT` instruction.

You can call the element `response` while reading data from `checkpoint_answers`. You can also add derived columns or use custom SQL. This separation is useful when the internal schema changes but you want to keep a stable backup format.

## 24.11 Element hierarchy

If an activity has criteria and responses, the tree might look like this:

```
checkpoint
    criteria
        criterion
    responses
        response
```

In code:

```php
$criteria = new backup_nested_element('criteria');
$criterion = new backup_nested_element(
    'criterion',
    ['id'],
    ['type', 'value', 'sortorder']
);

$responses = new backup_nested_element('responses');
$response = new backup_nested_element(
    'response',
    ['id'],
    ['userid', 'answertext', 'answerformat', 'grade', 'timemodified']
);

$checkpoint->add_child($criteria);
$criteria->add_child($criterion);

$checkpoint->add_child($responses);
$responses->add_child($response);
```

The hierarchy is not merely cosmetic. It determines data context, parent IDs, and processing order during restore.

## 24.12 `set_source_table()`

The simplest way to connect an element to data is `set_source_table()`.

```php
$checkpoint->set_source_table(
    'checkpoint',
    ['id' => backup::VAR_ACTIVITYID]
);
```

`backup::VAR_ACTIVITYID` represents the ID of the current activity instance being processed. This avoids receiving that ID manually from the URL or plugin configuration.

For child elements, we normally use the parent element ID:

```php
$criterion->set_source_table(
    'checkpoint_criteria',
    ['checkpointid' => backup::VAR_PARENTID]
);
```

## 24.13 `backup::VAR_PARENTID`

`VAR_PARENTID` allows an element's source to depend on the record currently being processed at the immediately higher level of the tree.

This is extremely useful in nested structures. The same `criterion` source can run for each parent checkpoint without the developer writing manual loops.

The backup engine traverses the tree and resolves these variables during execution.

## 24.14 `set_source_sql()`

When a simple table source is not enough, you can use parameterised SQL:

```php
$response->set_source_sql(
    "SELECT r.*
       FROM {checkpoint_answers} r
      WHERE r.checkpointid = :checkpointid",
    ['checkpointid' => backup::VAR_PARENTID]
);
```

Use SQL when you genuinely need a join, filter, or derived structure. Do not turn every element into custom SQL when `set_source_table()` is clearer.

## 24.15 User data and `$userinfo`

A backup can run with or without user data. The plugin must respect that setting.

```php
$userinfo = $this->get_setting_value('userinfo');
```

Criteria defined by the teacher are part of the activity structure and normally always belong in the backup. Learner responses are user data and should be included only when `$userinfo` is enabled.

```php
if ($userinfo) {
    $response->set_source_table(
        'checkpoint_answers',
        ['checkpointid' => backup::VAR_PARENTID]
    );
}
```

Do not ignore this option, because an administrator may be creating a backup of course structure only, with no personal data.

## 24.16 Structure without user data

Even when `$userinfo` is disabled, the `responses` element may still exist in the structure but have no data source, or you can organise the definition so that no records are generated.

What matters is the functional result: restoring the activity without users must recreate teacher configuration and content, but not responses, individual assessments, private logs, or other participant information.

## 24.17 `annotate_ids()`

One of the central restore problems is that IDs are not universal. User `15` on site A may be a different person on site B. Group `4` may not even exist on the destination.

When a field references an object that needs to be remapped, annotate that relationship:

```php
$response->annotate_ids('user', 'userid');
```

This tells backup that `response.userid` represents a user and allows restore to work with the corresponding mapping.

## 24.18 Annotating IDs does not change the value in the backup

`annotate_ids()` does not immediately replace the ID with another value. It records the dependency so the backup/restore mechanism knows that the reference needs special treatment.

The final translation happens during restore, once the destination environment already knows the mapping between the old ID and the new one.

This distinction explains why simply exporting `userid = 15` and inserting `15` on the destination is wrong.

## 24.19 Other annotatable references

Besides users, plugins may reference groups, course modules, questions, and other objects known to restore.

The annotation type needs to correspond to the mapping used by that subsystem. Do not invent arbitrary names without checking how that object will be mapped during restore.

When a reference belongs to an entity owned by the plugin itself, you normally create your own mapping while processing restore.

## 24.20 `annotate_files()`

Files stored through the File API do not need to be copied manually into XML. The structure annotates the file area:

```php
$checkpoint->annotate_files('mod_checkpoint', 'intro', null);
$checkpoint->annotate_files('mod_checkpoint', 'attachments', null);
```

The third argument represents the source of `itemid`. `null` is appropriate when the file area does not depend on a specific itemid, as with many areas associated directly with the activity context.

## 24.21 File area with `itemid`

If each response has attachments and the file area's `itemid` is the response ID, annotate the corresponding field:

```php
$response->annotate_files(
    'mod_checkpoint',
    'response_attachment',
    'id'
);
```

In this case restore also needs a mapping between the old response ID and the new one so the files can be placed under the correct item.

## 24.22 The mistake of copying physical paths

Never try to include `/moodledata/filedir/...` directly in an activity backup. The File API already abstracts storage, and Moodle may be using object storage, an alternative filesystem, or another implementation.

Backup works with file records and content through the files subsystem. The plugin provides component, filearea, and itemid, and core handles the transport.

## 24.23 `prepare_activity_structure()`

After building the tree, sources, and annotations, return the structure like this:

```php
return $this->prepare_activity_structure($checkpoint);
```

This helper adds the standard structure required by an activity and also supports integration with subplugins and other parts of the plan.

Copying a backup example from another plugin type and returning the raw element is a common mistake when the developer does not realise that activity modules have a specialised base class.

## 24.24 A complete `define_structure()`

For our example:

```php
protected function define_structure() {
    $userinfo = $this->get_setting_value('userinfo');

    $checkpoint = new backup_nested_element(
        'checkpoint',
        ['id'],
        ['name', 'intro', 'introformat', 'questiontext', 'questionformat',
         'grade', 'timeopen', 'timeclose', 'timemodified']
    );

    $criteria = new backup_nested_element('criteria');
    $criterion = new backup_nested_element(
        'criterion',
        ['id'],
        ['type', 'value', 'sortorder']
    );

    $responses = new backup_nested_element('responses');
    $response = new backup_nested_element(
        'response',
        ['id'],
        ['userid', 'answertext', 'answerformat', 'grade', 'timemodified']
    );

    $checkpoint->add_child($criteria);
    $criteria->add_child($criterion);
    $checkpoint->add_child($responses);
    $responses->add_child($response);

    $checkpoint->set_source_table(
        'checkpoint',
        ['id' => backup::VAR_ACTIVITYID]
    );

    $criterion->set_source_table(
        'checkpoint_criteria',
        ['checkpointid' => backup::VAR_PARENTID]
    );

    if ($userinfo) {
        $response->set_source_table(
            'checkpoint_answers',
            ['checkpointid' => backup::VAR_PARENTID]
        );
    }

    $response->annotate_ids('user', 'userid');

    $checkpoint->annotate_files('mod_checkpoint', 'intro', null);
    $response->annotate_files(
        'mod_checkpoint',
        'response_attachment',
        'id'
    );

    return $this->prepare_activity_structure($checkpoint);
}
```

This code already shows almost the entire backup philosophy because you describe the tree and dependencies instead of writing a procedural export row by row.

## 24.25 The generated XML

Conceptually, the result will be close to:

```html
<checkpoint id="42">
    <name>Weekly checkpoint</name>
    <grade>10</grade>
    <criteria>
        <criterion id="8">
            <type>submitted</type>
            <value>1</value>
        </criterion>
    </criteria>
    <responses>
        <response id="101">
            <userid>15</userid>
            <answertext>My response</answertext>
        </response>
    </responses>
</checkpoint>
```

Do not try to produce this XML manually. The engine generates it from the nested elements and their sources.

## 24.26 Backup task with multiple steps

Not every activity fits inside one structure step. Quiz is a familiar example of a more complex task because it needs to deal with questions and additional structures beyond the main configuration.

You can add more than one step:

```php
protected function define_my_steps() {
    $this->add_step(new backup_checkpoint_activity_structure_step(
        'checkpoint_structure',
        'checkpoint.xml'
    ));

    $this->add_step(new backup_checkpoint_extra_step(
        'checkpoint_extra'
    ));
}
```

Only do this when there is a genuinely separate responsibility. Splitting a small structure into five steps does not make the backup more professional.

## 24.27 Restore plan

Restore uses a mirrored architecture. A restore plan contains tasks and steps responsible for interpreting the backup structure and rebuilding the course at the destination.

Restore cannot simply insert XML as records because it has to remap IDs, create new contexts, rebuild course modules, restore files, and adjust internal references.

That is why processing order is essential.

## 24.28 Activity restore task

A restore task normally extends `restore_activity_task`:

```php
class restore_checkpoint_activity_task extends restore_activity_task {
    protected function define_my_settings() {
    }

    protected function define_my_steps() {
        $this->add_step(
            new restore_checkpoint_activity_structure_step(
                'checkpoint_structure',
                'checkpoint.xml'
            )
        );
    }
}
```

As in backup, the task coordinates the activity-specific steps.

## 24.29 `restore_activity_structure_step`

The restore structure step declares the XML paths it knows how to process:

```php
class restore_checkpoint_activity_structure_step
        extends restore_activity_structure_step {

    protected function define_structure() {
        $paths = [];
        $paths[] = new restore_path_element(
            'checkpoint',
            '/activity/checkpoint'
        );

        return $this->prepare_activity_structure($paths);
    }
}
```

When child elements exist, each path is declared as well.

## 24.30 `restore_path_element`

A `restore_path_element` connects a logical name to a path inside the XML.

```php
$paths[] = new restore_path_element(
    'criterion',
    '/activity/checkpoint/criteria/criterion'
);
```

The name `criterion` matters because the framework automatically looks for a `process_criterion()` method when it encounters that element.

## 24.31 `process_*()`

The convention is straightforward:

```
checkpoint -> process_checkpoint()
criterion  -> process_criterion()
response   -> process_response()
```

This keeps the structure declaration readable and divides persistence code according to the type of element being restored.

## 24.32 Restoring the main instance

The root element is normally processed like this:

```php
protected function process_checkpoint($data) {
    global $DB;

    $data = (object)$data;
    $oldid = $data->id;

    $data->course = $this->get_courseid();
    $data->timemodified = time();

    $newid = $DB->insert_record('checkpoint', $data);

    $this->apply_activity_instance($newid);
}
```

The most important detail is `apply_activity_instance()`.

## 24.33 `apply_activity_instance()`

After inserting the main activity record, restore needs to know which new instance was created so it can associate it with the new course module.

```php
$this->apply_activity_instance($newid);
```

This call should happen immediately after creating the main record, according to the activity restore-step contract.

Forgetting it usually results in an incompletely created activity or later restore errors.

## 24.34 Old ID and new ID

During restore almost every element conceptually has two IDs. The `oldid` came from the source site and the `newid` was created on the destination.

```php
$oldid = $data->id;
$newid = $DB->insert_record('checkpoint_criteria', $data);
```

Restore needs to store that relationship when other records or files depend on it.

## 24.35 `set_mapping()`

Plugin-owned mappings are registered with `set_mapping()`:

```php
$this->set_mapping('checkpoint_criterion', $oldid, $newid);
```

Now an element processed later can translate an old reference to the corresponding new record.

The first argument is the logical mapping name, and it must be used consistently throughout the rest of the restore.

## 24.36 Restoring child elements

Criteria can be recreated like this:

```php
protected function process_criterion($data) {
    global $DB;

    $data = (object)$data;
    $oldid = $data->id;

    $data->checkpointid = $this->get_new_parentid('checkpoint');

    $newid = $DB->insert_record('checkpoint_criteria', $data);
    $this->set_mapping('checkpoint_criterion', $oldid, $newid);
}
```

The parent ID from the backup must not be used directly because the new instance has another ID.

## 24.37 `get_new_parentid()`

When an element is nested inside another element in the structure, the framework maintains information about the parent currently being restored.

```php
$data->checkpointid = $this->get_new_parentid('checkpoint');
```

This avoids manually creating a mapping for every parent-child relationship when the hierarchy already expresses the dependency.

## 24.38 `get_mappingid()`

When you need to translate another ID that was annotated or mapped, use `get_mappingid()`:

```php
$data->userid = $this->get_mappingid('user', $data->userid);
```

The result is the corresponding user ID on the destination. If no mapping exists, the behaviour must be handled according to the data type and restore contract.

## 24.39 A user that does not exist on the destination

Not every restore includes creation or matching of every user. If a response depends on a user that was not restored, the plugin must respect the restore process.

Do not invent user `0`, do not preserve the old ID, and do not assign the response to the current user. Use the mappings provided by restore and define how the entity should behave when its owner is unavailable.

## 24.40 Restoring user responses

An example:

```php
protected function process_response($data) {
    global $DB;

    $data = (object)$data;
    $oldid = $data->id;

    $data->checkpointid = $this->get_new_parentid('checkpoint');
    $data->userid = $this->get_mappingid('user', $data->userid);

    if (!$data->userid) {
        return;
    }

    $newid = $DB->insert_record('checkpoint_answers', $data);

    $this->set_mapping(
        'checkpoint_response',
        $oldid,
        $newid,
        true
    );
}
```

The fourth parameter, `true`, is used when the mapping needs to participate in file mappings, for example for file areas whose itemid is that record.

## 24.41 Restore mappings are the backbone

Many restore bugs are really mapping bugs. The main data is recreated correctly, but a child still points to the old ID; a file is restored, but under the wrong itemid; a reference to another activity remains a raw number.

During review, look at every column ending in `id` and ask whether it is local to the record or references an entity that will change on the destination.

## 24.42 Restoring files

Files annotated during backup need to be added during restore:

```php
protected function after_execute() {
    $this->add_related_files('mod_checkpoint', 'intro', null);
    $this->add_related_files('mod_checkpoint', 'attachments', null);
}
```

For file areas associated with mapped item IDs:

```php
$this->add_related_files(
    'mod_checkpoint',
    'response_attachment',
    'checkpoint_response'
);
```

The third argument in this context identifies the mapping that should be used for itemid.

## 24.43 `after_execute()`

`after_execute()` runs after the structure elements have been processed. This is an ideal time for files because the required mappings have already been created.

It can also be useful for small adjustments that depend on the whole structure being available, but do not turn `after_execute()` into a generic second restore phase for everything. The earlier a relationship can be rebuilt correctly in `process_*()`, the clearer the flow remains.

## 24.44 File areas and mappings

Suppose that on site A response `101` has a file with `itemid = 101`. On site B the same response became `389`.

If restore simply recreates the file record with the old itemid, the file will exist but will be disconnected from the response. The `checkpoint_response` mapping is the link that tells the File API that `101` now means `389`.

This is one reason not to test backup merely by checking whether the activity appears. Open the restored attachments.

## 24.45 User-dependent content

Besides deciding whether an element is included when `$userinfo` is enabled, you need to inspect everything that depends on a user. Responses, attempts, individual feedback, participation timestamps, and files uploaded by learners are normally user data.

Activity configuration, a teacher-created question, and completion criteria normally belong to the activity structure, although the original author may exist as metadata in some cases.

Classification must follow the meaning of the data, not merely the presence of a `userid` column.

## 24.46 Gradebook in backup

Activity modules that integrate with the Gradebook normally should not try to export Gradebook internal tables directly. The course backup infrastructure already knows about grade items and grades.

The plugin needs to ensure that its own restored state is consistent with how the Gradebook will be rebuilt and that grade callbacks work after restore.

If there is internal data used to calculate a grade, that data may belong in the plugin backup. The official Gradebook grade still belongs to the appropriate subsystem.

## 24.47 Completion in backup

Completion configuration is associated with the course module and is handled by core. The plugin should not duplicate completion flags inside the activity XML merely to "make sure they come back".

What belongs to the plugin are its own fields supporting custom rules, for example `requirefeedback = 1`. Those fields need to be transported because they are part of the activity configuration.

## 24.48 Groups and groupings

If plugin-owned data stores `groupid` or `groupingid`, those references need appropriate annotations and mappings.

Do not copy a raw `groupid` into restore. Even if the restored course contains equivalent groups, the physical IDs will be different.

## 24.49 Internal links in content

HTML text may contain absolute links to Moodle pages, for example:

```
https://source.example/mod/checkpoint/view.php?id=123
```

If that content is restored on another domain and the link remains unchanged, it will point back to the old site.

That is why backup has a link-encoding mechanism and restore has decoding rules.

## 24.50 `encode_content_links()`

The activity task can replace links with portable tokens:

```php
public static function encode_content_links($content) {
    global $CFG;

    $base = preg_quote($CFG->wwwroot, '/');

    $search = "/({$base}\/mod\/checkpoint\/view.php\?id=)([0-9]+)/";

    return preg_replace(
        $search,
        '$@CHECKPOINTVIEWBYID*$2@$',
        $content
    );
}
```

You do not need to encode URLs that do not belong to the component or that are already handled by another subsystem.

## 24.51 Decoding content

In the restore task, `define_decode_contents()` tells Moodle which fields need their tokens decoded:

```
public static function define_decode_contents() {
    return [
        new restore_decode_content(
            'checkpoint',
            ['intro', 'questiontext'],
            'checkpoint'
        ),
    ];
}
```

The rule needs to point to the fields where those links may exist.

## 24.52 `define_decode_rules()`

Then we define how the token becomes a destination URL again:

```
public static function define_decode_rules() {
    return [
        new restore_decode_rule(
            'CHECKPOINTVIEWBYID',
            '/mod/checkpoint/view.php?id=$1',
            'course_module'
        ),
    ];
}
```

The `course_module` mapping allows the old cmid to be replaced with the new one.

## 24.53 Encoded links are different from files

`@@PLUGINFILE@@` and internal activity URLs solve different problems. Embedded files use the File API and its own restore process, while links to Moodle pages may need encode/decode rules.

Mixing the two concepts usually results in regular expressions trying to fix a file URL that core should already handle.

## 24.54 Domain changes

A good restore test should not use only the same hostname. If possible, restore the backup on an installation with a different URL.

This exposes forgotten absolute links, improper external references, and hidden dependencies on the old `$CFG->wwwroot`.

## 24.55 Subplugin backup

When an activity has subplugins, the parent needs to provide integration points so each child can add its part of the structure.

The backup mechanism has helpers such as `add_subplugin_structure()`, used by extensible plugins such as Assignment, Quiz, and Workshop.

The idea is the same as in Chapter 20: the parent knows the subplugin type and provides connection points, but should not know the specific data owned by each child.

## 24.56 `add_subplugin_structure()`

Conceptually, the parent adds structures supplied by subplugins at a particular point in the tree.

Instead of writing:

```php
if ($plugin === 'mychild') {
    // Export specific data.
}
```

It delegates to the subplugin backup mechanism and each implementation describes its own content.

This preserves extensibility during backup/restore too, which is exactly where modular architectures tend to break if the host was designed only for runtime.

## 24.57 Subplugin restore

During restore the process is reversed. The host provides connection points, and each subplugin processes its paths, mappings, and files.

If a subplugin is absent from the destination, behaviour needs to follow the host and restore contract. A fatal error simply because an optional component from site A does not exist on site B is not acceptable.

Depending on the plugin type, restore may warn, ignore that portion, or require the component to be installed before continuing.

## 24.58 Activity modules

Activity modules have the best-known backup path. They use `backup_activity_task`, `backup_activity_structure_step`, `restore_activity_task`, and `restore_activity_structure_step`.

When an activity declares `FEATURE_BACKUP_MOODLE2`, it is telling core that it implements this mechanism.

Do not declare the feature and leave the files half implemented, because duplication and import may offer options that later end in errors.

## 24.59 Blocks

Blocks also have specific support inside course backup. Instance configuration can be transported by the block mechanism, while additional data requires proper participation in the API.

What we discussed in Chapter 16 still applies: a custom table belonging to a block does not enter backup merely because it contains `blockinstanceid`.

## 24.60 Local plugins

Local plugins have a specialised `backup_local_plugin` class precisely because some of them can attach course-related data to backup connection points.

That does not mean every `local` plugin should enter an `.mbz`. If a table is global, represents institutional configuration, or belongs to an integration independent of a course, placing that data in every backup would be conceptually wrong.

First determine whether the data belongs to the course, then implement the appropriate connection point.

## 24.61 Enrolment plugins

Enrolment has its own support because method instances and enrolments participate in the course.

Restore needs to decide how to recreate instances and enrolments while respecting user settings and method policies. We discussed this in Chapter 18, and here it becomes clear why an `enrol` plugin cannot simply export `user_enrolments` as an ordinary table.

## 24.62 Course formats

Course formats also have a specialised backup plugin class. A format can store options or data linked to course structure and participate through suitable connection points.

Because a format controls presentation and organisation of sections, references to restored sections need to follow mappings for the new course.

## 24.63 Admin tools

Admin tools have specific support with classes such as `backup_tool_plugin` and `restore_tool_plugin` for cases where the tool genuinely owns course data that needs to accompany the backup.

Again, do not confuse API availability with an obligation to export global administrative configuration.

## 24.64 Themes and reports

Core documentation also contains specific connection points for themes and reports in contexts supported by the backup plan.

This is useful for dismantling the idea that `backup/moodle2` belongs only to `mod`, but it also shows why we cannot generalise that "every plugin supports backup automatically". Each plugin type needs to be connected to the plan through its own infrastructure.

## 24.65 Question types and Question Engine

Questions are a more complex case because they can be shared, versioned, and referenced by several activities. The Question Engine has specific backup integration for transporting Question Bank entries, versions, categories, usages, and references when required.

A qtype implements its own points for options, answers, and additional structures instead of treating question tables as private activity data.

Chapter 22 already showed why copying a raw `question.id` between installations would be disastrous.

## 24.66 Advanced grading methods

Grading forms and other subplugins can also participate in backup through points provided by the corresponding subsystem.

The pattern is the same: the component that owns the structure creates the connection point and the subplugin describes what needs to be transported.

## 24.67 Common mistake with `backup_nested_element`

A classic mistake is creating an element and forgetting to attach it to the tree:

```php
$response = new backup_nested_element(...);
$response->set_source_table(...);
```

But never doing:

```php
$responses->add_child($response);
```

The code looks complete and the source exists, but the element is not part of the returned structure and will not be exported.

## 24.68 `backup_nested_element` errors

Another group of errors appears when a developer tries to reuse the same element under more than one parent, creates names incompatible with restore paths, or defines fields that do not exist in the source.

When an error mentions `backup_nested_element`, do not fix it by randomly changing arrays. Return to three questions: which parent is this element attached to, does the source provide exactly the declared fields, and does the tree represent a valid hierarchy?

## 24.69 Source and fields must match

If a nested element declares:

```
['userid', 'grade', 'timemodified']
```

but the SQL returns `user_id` instead of `userid`, the structure will not receive the expected value.

SQL aliases are perfectly valid, but they must match the field name declared in the element.

## 24.70 Do not include unnecessary derived IDs

If `checkpointid` can be reconstructed from the parent relationship during restore, there is often no reason to persist that field in XML as business information.

The fewer internal IDs you transport without need, the lower the risk of accidentally reusing old values.

## 24.71 Version compatibility

Backup is also an interchange format between versions. A plugin may create a backup in one version and restore it in a newer one.

That means schema changes need to consider restoring old backups. If you added a field in version 2.0, `process_checkpoint()` needs to know how to handle XML from 1.5 where that field does not exist.

Use deliberate defaults when the information did not exist in the older version.

## 24.72 Restoring an old backup

A common pattern is:

```php
if (!isset($data->newsetting)) {
    $data->newsetting = 0;
}
```

This allows the current version to restore backups created before that setting existed.

Do not require an old backup to contain a field it could never have generated.

## 24.73 Removing a plugin field

If a field no longer exists in the current schema, restore may simply ignore the old information, provided no semantic migration is needed.

Do not keep an obsolete database column merely because old backups still carry the value.

Compatibility belongs in the restore layer, not in freezing the schema forever.

## 24.74 Migration during restore

Sometimes an old field needs to be transformed into a new structure. `process_*()` is a good place to convert the received format before insertion.

This is different from `db/upgrade.php`. Upgrade transforms an existing installation; restore transforms a backup package into new data on the current installation.

## 24.75 Duplication uses backup/restore

When a teacher clicks Duplicate on an activity, Moodle uses the backup and restore infrastructure.

This is one of the most practical reasons to implement backup early. You do not need to wait for someone to migrate a course to another server before discovering that it is broken; an everyday authoring workflow may already depend on it.

## 24.76 Import between courses

Importing activities from another course also goes through this infrastructure. The destination may have completely different courseid, sectionid, groupids, and contextids.

If your code depends on absolute IDs persisted inside text fields or JSON without mappings, import tends to expose the problem.

## 24.77 External data should not be copied blindly

An activity may store the identifier of an external resource, such as a videoconference room or an object in an ERP. Duplicating the activity does not necessarily mean the destination should point to the same resource.

The plugin needs to decide whether that identifier is portable configuration, should be cleared during restore, or should trigger creation of a new external resource.

This is a domain decision, and backup is where it needs to become explicit.

## 24.78 Tokens and secrets

Tokens, passwords, and API keys normally do not belong in a course backup. If a sensitive field exists in the activity table, do not automatically include it in the nested element merely because it appears in `install.xml`.

Consider whether the secret is global, whether it should be reconfigured on the destination, and whether exporting it would create a security risk.

A functional backup does not mean copying every available value.

## 24.79 Logs

Modern logs are generated by Events, and core normally has its own rules for restoring logs where applicable.

An activity should not create a parallel log table just to be able to transport it. If a domain log is essential, treat it as plugin data; if it is technical audit data, it probably does not need to travel with the activity.

## 24.80 `define_restore_log_rules()`

Older activities or flows that need to restore logs can define rules:

```
public static function define_restore_log_rules() {
    return [
        new restore_log_rule(
            'checkpoint',
            'view',
            'view.php?id={course_module}',
            '{checkpoint}'
        ),
    ];
}
```

In current development, first understand whether this is genuinely needed by the plugin rather than copying historical rules with no purpose.

## 24.81 Testing backup of the activity in isolation

Create an instance containing everything the plugin supports: an intro with an image, criteria, dates, files, user responses, a grade, and custom settings.

Generate a backup of only that activity with user data enabled and inspect the restored activity in another course.

Then repeat without user data.

## 24.82 What to verify after restore

Do not stop at checking that the name appeared. Confirm:

```
instance configuration
child records
intro files
files per response
user mappings
grades
completion configuration
internal links
calendar events where applicable
subplugins
expected permissions
```

Any part derived from the activity can reveal a forgotten mapping or cleanup step.

## 24.83 Restore on another site

The most valuable test is site A -> `.mbz` -> site B.

Use another database, another hostname, and different IDs. If possible, create users and courses in a different order to ensure old IDs do not happen to match.

Many plugins appear to restore correctly on the same site only because `userid = 15` still refers to the same person.

## 24.84 Test without the plugin installed

Try restoring a backup containing your activity on a site where the plugin is not installed. Observe Moodle's message and understand the behaviour.

Then install the plugin and repeat. This helps document restore dependencies for administrators.

## 24.85 Test with a newer plugin version

Create a backup with an older version of the plugin and restore it using the current version.

This is the test that validates real format compatibility and the defaults used for fields added later.

If every release changes the XML without considering previous versions, backup becomes fragile exactly when it is most needed.

## 24.86 PHPUnit for backup/restore

Much of this flow can be automated. A test can create a course, user, activity, and child data, run backup and restore, and then compare the result.

This kind of test costs more than a simple unit test, but it is extremely valuable for plugins with complex structures.

In Chapter 25 we will go deeper into PHPUnit infrastructure, but it is already worth writing production code in a way that makes restored state easy to validate.

## 24.87 Do not test by comparing IDs

After restore the IDs should change. A test expecting `newid === oldid` validates exactly the wrong thing.

Compare content and relationships:

```
same name
same criteria
same number of responses
user correctly mapped
files present
links pointing to the new cmid
```

## 24.88 Backup performance

Backup can process huge volumes, especially when user data is included. Do not load millions of responses into a PHP array before generating the structure.

The backup framework and its sources exist precisely to process data in a controlled way.

Avoid N+1 queries in callbacks and unnecessarily complex sources.

## 24.89 Indexes still matter

A source filtering `checkpointid` in a table containing millions of responses needs a suitable index.

Backup does not magically become fast because it runs in cron or CLI. A bad query executed hundreds of times remains bad.

The same principles from Chapters 5 and 12 still apply.

## 24.90 Memory

Avoiding manual serialisation into giant arrays helps keep memory use predictable.

Also be careful in `after_execute()` not to load all mappings or files at once when the subsystem already provides incremental methods.

Large-course backup is an excellent place for small memory decisions to become production failures.

## 24.91 Restore idempotency does not mean running twice

Restore is normally a controlled process and is not designed to insert the same structure repeatedly inside the same task. Even so, each `process_*()` should assume source IDs are not trustworthy on the destination and that every relationship passes through mappings.

Do not use "a record with this ID already exists" as a deduplication strategy.

## 24.92 Partial errors

If restore fails halfway through, the controller and framework manage the overall operation. Do not catch every exception inside `process_*()` and silently continue.

Ignoring a mapping error can produce a course that appears restored but is internally corrupted.

Fail with enough context when the structure cannot be reconstructed correctly.

## 24.93 Diagnosing restore

When something fails, first identify which layer failed:

```
plan
activity task
structure step
process_*()
mapping
files
link decoding
subplugin
```

This classification greatly reduces random attempts to modify XML because each layer has different responsibilities.

## 24.94 Do not edit `.mbz` manually to fix a plugin

Editing backup XML can be useful for diagnosis, but it is not a plugin fix.

If the generated backup is wrong, fix backup. If an old package needs compatibility, fix restore. Manually transforming files does not scale and does not solve duplication or future restores.

## 24.95 Complete restore example

A summarised `restore_checkpoint_stepslib.php` could look like this:

```php
class restore_checkpoint_activity_structure_step
        extends restore_activity_structure_step {

    protected function define_structure() {
        $paths = [];

        $paths[] = new restore_path_element(
            'checkpoint',
            '/activity/checkpoint'
        );
        $paths[] = new restore_path_element(
            'criterion',
            '/activity/checkpoint/criteria/criterion'
        );
        $paths[] = new restore_path_element(
            'response',
            '/activity/checkpoint/responses/response'
        );

        return $this->prepare_activity_structure($paths);
    }

    protected function process_checkpoint($data) {
        global $DB;

        $data = (object)$data;
        $data->course = $this->get_courseid();

        $newid = $DB->insert_record('checkpoint', $data);
        $this->apply_activity_instance($newid);
    }

    protected function process_criterion($data) {
        global $DB;

        $data = (object)$data;
        $oldid = $data->id;
        $data->checkpointid = $this->get_new_parentid('checkpoint');

        $newid = $DB->insert_record('checkpoint_criteria', $data);
        $this->set_mapping('checkpoint_criterion', $oldid, $newid);
    }

    protected function process_response($data) {
        global $DB;

        $data = (object)$data;
        $oldid = $data->id;
        $data->checkpointid = $this->get_new_parentid('checkpoint');
        $data->userid = $this->get_mappingid('user', $data->userid);

        if (!$data->userid) {
            return;
        }

        $newid = $DB->insert_record('checkpoint_answers', $data);
        $this->set_mapping('checkpoint_response', $oldid, $newid, true);
    }

    protected function after_execute() {
        $this->add_related_files('mod_checkpoint', 'intro', null);
        $this->add_related_files(
            'mod_checkpoint',
            'response_attachment',
            'checkpoint_response'
        );
    }
}
```

The example is small enough to read, but it already contains the points that usually separate a functional restore from one that only appears to work.

## 24.96 What I look for in code review

When I review a plugin backup, I start by looking at its custom tables and classifying which ones hold configuration, child data, and user data. Then I look for every field that references IDs outside its own table and check annotations or mappings. Next I inspect file areas, internal links, and subplugins.

On restore, I verify that the main record calls `apply_activity_instance()`, that children use the new parent, that mappings are created before they are used, and that `after_execute()` restores files with the correct mapping.

Finally, I test duplication because it tends to expose problems quickly.

## 24.97 Exercise - backup on site A and restore on site B

Extend `mod_checkpoint` so it has the main table, at least two configuration criteria, user responses, and a `response_attachment` file area whose `itemid` is the response ID.

Implement `backup_checkpoint_activity_task`, `backup_checkpoint_activity_structure_step`, `restore_checkpoint_activity_task`, and `restore_checkpoint_activity_structure_step`. Criteria should always be included; responses and their attachments only when user info is enabled.

Annotate `userid`, annotate the file areas, and create a custom mapping for responses. Add an HTML string in `questiontext` containing a link to another `mod_checkpoint` instance and implement encode/decode so the link is rewritten to the new destination cmid.

Then run four scenarios. First, backup and restore in the same course through duplication. Second, course backup without users. Third, a complete backup from site A to site B with a different hostname and different IDs. Fourth, a backup created by an older plugin version where a new configuration field did not yet exist.

The exercise is only complete when attachments open, users are correct, links point to the destination, no responses appear in a backup without user data, and the current version restores the old package using a coherent default.

## 24.98 What you should take away from this chapter

Backup and restore are not side features of a Moodle activity. They are part of the normal authoring lifecycle because duplication and import depend on the same infrastructure.

The main idea is to separate structure, dependencies, and identity. `backup_nested_element` describes the tree, sources say where data comes from, annotations register references that will need treatment, files are connected through file areas, and restore reconstructs everything using mappings instead of trusting old IDs.

It should also be clear that `backup/moodle2` does not belong exclusively to activity modules, but backup support depends on the connection points provided for each plugin type. Creating a folder with that name does not automatically make a global table appear in an `.mbz`.

When backup is implemented correctly, the most important result is precisely the absence of surprises: the teacher duplicates, imports, or restores, and the activity continues working as though it had been created on the destination because every ID, file, and reference was reconstructed through the correct contract.
